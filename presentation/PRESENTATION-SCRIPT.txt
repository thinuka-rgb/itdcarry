SLIDE 1 — 0:00–0:20 (20 seconds)
Same DNA. Different answer?
[Click to this slide.]
Hello, I’m Thinuka. Imagine giving two versions of a program the same DNA data and getting different answers. ITDcarry asks a simple question: can changed software still find the exact DNA marker we already know is there? This is a synthetic software experiment.

SLIDE 2 — 0:20–0:50 (30 seconds)
One threshold. A different result.
[Click to this slide.]
Here is the problem in this example. The data has four unique supporting reads—four distinct pieces of supporting sequence evidence. One profile requires two, so it finds the marker. Change that requirement to five, and the same input no longer produces the exact high-confidence result. The DNA has not changed. The software setting has. That makes comparability worth checking.

SLIDE 3 — 0:50–1:20 (30 seconds)
Challenge it. Then compare exactly.
[Click to this slide.]
ITDcarry keeps a precise description of a known DNA pattern called an FLT3-ITD. It creates controlled synthetic reads and challenges the pipeline with them. Then it checks three things: the marker’s position, its length, and its DNA sequence. All three must match. In this example, the target is twenty-one bases long, at position seventy-two in the caller’s reference.

SLIDE 4 — 1:20–2:00 (40 seconds)
Demo: same input, two runs.
[Click to this slide.]
This is a replay of real local results from the repository’s core code. First, we verify the input files and known marker.

The compatible profile finishes successfully. It recovers the exact position, length and sequence, with four unique supporting reads.

Now the changed profile requires five. It also finishes successfully, but does not recover the exact marker.

The local reference result is ‘not technically comparable.’ The setting changed; the marker did not.

SLIDE 5 — 2:00–2:35 (35 seconds)
A check on software.
[Click to this slide.]
The useful result is an explanation we can inspect: this particular software change loses the exact marker in this synthetic challenge. The full repository workflow also uses Daytona for execution and Neo4j for provenance and the verdict; those cloud services were not run in this local demo. This proof of concept does not diagnose disease, determine treatment, or validate the laboratory process. It checks software behavior.

SLIDE 6 — 2:35–3:00 (25 seconds)
The proposal.
[Click to this slide.]
I’m asking for approval to present ITDcarry as a supervised school demonstration, with peer feedback and teacher guidance. A next step would be testing more synthetic cases and documenting where it works and where it fails. The question I want you to remember is: before comparing the answer, have we checked what the software can still see? Thank you.
